# 4. Arquitetura e Decisões de Projeto

## 🧠 Princípio Central

Estruturar o sistema em módulos com responsabilidade clara, de forma que:

- Cada módulo tenha um propósito bem definido
- A troca de um módulo seja menos custosa
- Testes, revisões e evolução sejam mais simples

## 🗂️ Separação de Responsabilidades Sugerida

| Camada / Módulo | Foco |
| :--- | :--- |
| **Módulo de Autenticação** | Login, sessão/estado de acesso, proteção de rotas |
| **Módulo de Cadastros** | Usuários, máquinas, suprimentos, equipamentos portáteis |
| **Módulo de Manutenção** | Registro, histórico, relatórios e gráficos |
| **Módulo de Produção** | Registro de impressão/escaneamento, consumo de insumo |
| **Módulo de Estoque** | Entrada, saída fracionada, saldos |
| **Módulo de Empréstimo** | Inventário portátil, retirada, devolução |
| **Módulo de Relatórios** | Listagens, consolidados e filtros por período |

## 📐 Defensibilidade do Projeto

- Não acumular regras em uma única tela ou bloco gigante.
- Cada domínio trabalha com seus próprios dados e responsabilidades.
- Relatórios devem consumir dados validados, não ficar "no improviso".

## ⚖️ Decisões que Podem Mudar com o Tempo

- Forma de armazenamento e consulta dos dados
- Extensão de relatórios e filtros
- Grau de automação na emissão de registros
- Ajustes de permissões por perfil

> **Regra de ouro:** toda decisão que altere responsabilidade de módulos deve ser registrada aqui ou em um arquivo de racional mais específico.
